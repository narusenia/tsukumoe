# 性能目標の測定と達成

- REQ: REQ-PERF-002, 003, 004, 005, 006, 009（007 は保留）
- 単位: M3-07
- 状態: 実施済み（PERF-006 は僅差で未達。相談あり）
- 依存: M3-01（M3-04 の WASM 計測を含む）
- 基準モデル: `assets/reference-model/parts.json` から `tsukumoe generate` で生成する（ArtMesh 150・頂点 3 万・パラメータ 100・デフォーマ 80・物理 20）

## 目的

性能目標を、再現できる手順で測り、数字で達成を示す。未達の項目は、原因と次の手を記録する。

## 基準環境

測定は、開発者の手元（Apple M5、macOS）を基準環境とする。他の環境の数値は参考値として記録し、合否には使わない。CI（ubuntu）のベンチは、絶対値ではなく回帰検知（PERF-009）に使う。

## 項目ごとの測り方

| REQ | 項目 | 測り方 | 合格 |
|---|---|---|---|
| PERF-002 | ネイティブの評価時間 | criterion の `reference_evaluate`（パラメータ入力から描画リストまで、1 スレッド）の中央値 | 0.5 ms 以下 |
| PERF-003 | WASM の評価時間 | M3-04 の検証ページで、SIMD 有りの `update` を Chrome 安定版で繰り返し測った中央値 | 2 ms 以下 |
| PERF-004 | 参照レンダラの GPU 時間 | `tsukumoe-gpu` で 1080p の基準モデルを描き、タイムスタンプクエリで GPU 時間の中央値を測る | 1 ms 以下 |
| PERF-005 | ロード時間 | `.tmod`（M3-01）の読み込み（検証込み、テクスチャのデコードを除く）を criterion で測る | 20 ms 以下 |
| PERF-006 | 多数体の同時表示 | 基準モデル 50 体を、評価（`update`）と 1080p の描画まで 1 フレームで行い、フレーム時間の中央値と 99 パーセンタイルを測る | 16.6 ms 以下 |
| PERF-009 | 回帰検知 | CI のベンチを main の結果と比べ、閾値（10%）を超える劣化で失敗させる | 劣化の模擬で失敗する |

## 方針

- 測定コードは `crates/*/benches/` と `examples/` に置き、手順は `docs/dev/performance.md` に書く（コマンドと、結果の読み方）。結果の数値は、`docs/implementation/M3-runtime/performance.md` の「結果」節に日付つきで記録する（PERF-007 のような非公開の比較は含まない）
- 現在の `scripts/bench-budget.json` は上限（天井）で、PERF-002 の 0.5 ms より緩い。合格後に、目標に合わせて天井を締める（実測の 2 倍程度を余裕とする）
- 未達の項目は、プロファイル（`cargo flamegraph` 等は使わず、まず区間ごとの時間を計る計測を足す）で原因を特定し、まず低い工数の対処（ホットな配列の見直し、不要な再計算の除去）を試す。SIMD 化や GPU 変形は、必要が示されてから別の判断にする
- PERF-009 は、criterion の `--save-baseline` と比較（`critcmp` などの新しいツールは使わず、既存の `check-bench.sh` に main の結果との比較を足す）。main の結果の保存方法（CI のキャッシュまたは成果物）は、実装時に決めて記録する

## 結果

手順は `docs/dev/performance.md`。基準環境は Apple M5、macOS、Chrome 安定版。

### 2026-10-31

| REQ | 測定値 | 目標 | 合否 |
|---|---|---|---|
| PERF-002 | `reference_evaluate` 0.146 ms（中央値） | 0.5 ms 以下 | 合格 |
| PERF-003 | Chrome、SIMD 有り（`opt-level=z`）、`update` 0.352 ms（15 回 × 300 回の各平均の中央値。範囲 0.351〜0.361） | 2 ms 以下 | 合格 |
| PERF-004 | 1080p の基準モデル、完了待ち時間の中央値 0.22〜0.36 ms（GPU 時間の上限。実行ごとの幅） | 1 ms 以下 | 合格（上限で）。下記 |
| PERF-005 | `reference_load` 0.335 ms（2.4 MB のファイル読み込み + 検証）。検証だけ 0.148 ms | 20 ms 以下 | 合格 |
| PERF-006 | 50 体、1080p、`update` から GPU 完了まで: 中央値 17.0 ms、99 パーセンタイル 18.5 ms（`update` 7.4 ms を含む） | 16.6 ms 以下 | 未達（僅差）。下記 |
| PERF-009 | main との比較を `check-bench.sh` と CI に追加。ベンチに 30 µs の遅延を入れ、中央値 175.9 µs（基準 145.7 µs、+21%）で失敗することを確認し、遅延は戻した | 劣化の模擬で失敗 | 合格 |

PERF-003 と同じページで、WebGPU・WebGL2 とも native との画素差は最大 0/255（基準モデル、512x512）。描画の変更（下記）の後に確認した。

#### PERF-004

- Metal のタイムスタンプクエリは使えない: 機能は有効になるが、同じパスの中でも終了の値が開始より前になる（200 回中 189 回、差の中央値 -1.15 ms）。代わりに、submit の後に GPU の完了を待った時間を測った（提出の遅れを含む上限）
- 最初の計測（最適化前）は 5.76 ms で不合格だった。原因は、描画リストの 1 メッシュごとに render pass を開き、1080p のターゲットを毎回 load/store していたこと（150 パス）

#### 最適化の前後（参照レンダラ、`tsukumoe-gpu`）

出力は変わらない（`tsukumoe-gpu` と `tsukumoe-cli` の既存テストが通る。ブラウザでも native と同一）。`update` は 7.3 ms で、各行の PERF-006 に含まれる。行の順に、前の行の変更に積み重ねる（途中の行は、体ごとに `update` を済ませてから描く旧い計測）。

| 変更 | PERF-004 | PERF-006 の中央値 |
|---|---|---|
| 最適化前 | 5.76 ms | 306.9 ms |
| マスクの無い描画を 1 つの render pass にまとめる | 0.48 ms | 61.7 ms |
| 描画ごとの uniform を 1 つのバッファと動的オフセットにする | 0.38 ms | 22.1 ms |
| 頂点・インデックス・uniform のバッファを呼び出し間で使い回す | 0.31 ms | 20.4 ms |
| 変わらない UV とインデックスを送り直さない | 0.29 ms | 16.65 ms |
| 同じ render pass で束縛済みの状態を設定し直さない | 0.22〜0.34 ms | 16.7 ms |
| 体ごとに評価と提出を交互に行う計測に変更（最終） | 0.22〜0.36 ms | 16.9〜17.1 ms |

#### PERF-006 が未達の理由と次の手

- 内訳（1 フレーム 約 17 ms）: 50 体の `update` 7.3〜7.9 ms、描画の CPU 側 約 7 ms（1 体あたり 140 µs: 頂点の転送 54、uniform 11、記録 8、検証（`finish`）52、提出 9）、最後の GPU 待ち 約 2 ms
- 解像度を 480x270 に下げても 16.96 ms で変わらないため、GPU の塗りは支配的でない
- 評価（1 スレッド 0.146 ms/体）が約 45% を占め、残りは体ごとの提出のコスト。これ以上は低い工数の対処が残っていない
- 参考（採用していない実験）: 50 体の `update` を 7 スレッドに分けると、中央値 10.1 ms、99 パーセンタイル 12.4 ms になった（`update` 1.9 ms）。ブラウザ（WASM）はこの手が使えない
- 相談: (1) 体ごとの評価を並列化する前提で目標を判定するか、(2) 複数の描画リストを 1 つの render pass と 1 回の提出にまとめる API を足すか、(3) 評価の SIMD 化に進むか

#### PERF-007（保留）

- 理由: 同じ基準モデルの Live2D 形式版が要り、M2 の法務ゲートと検証モデルの作成（M2-02・M2-03）の後でないと作れない
- 再開の条件: M2-02・M2-03 が完了し、Live2D 形式の基準モデルがあること。手順の記録だけを `docs/dev/` に置く（非公開の比較なので、数値は含めない）

#### PERF-009 の保存方法

- main の結果は GitHub Actions のキャッシュに保存する（成果物ではなく）。pull request は最新のキャッシュを復元して比べる。成果物は他の実行から取り出すのに API の認証が要るため
- 注意: ubuntu の共有ランナーのゆらぎで誤検知する可能性がある。キャッシュは 7 日アクセス無しで消え、その間は比較を飛ばす。ランナーは基準環境ではないので、CI の天井は 4 倍に緩め、劣化は比較で見る

#### 天井（`scripts/bench-budget.json`）

実測の 2 倍程度に締めた（`compile` 330 µs、`reference_evaluate` 300 µs など）。0.5 ms を超える天井は、未達の PERF-006 の `frame_reference_x50_1080p`（20 ms）と `_p99`（22 ms）、50 体の評価 `reference_advance_x50`（15 ms）で、目標が 16.6 ms の複数体のため。
