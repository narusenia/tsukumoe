# macOS のネイティブメニュー（`tsukumoe-app`）

- REQ: なし（M5-02 の UX 改善の延長。REQ-UI-004 のテーマ・キーマップ層を使う）
- 単位: M5-02a
- 状態: 計画中
- 依存: M5-02
- クレート: `tsukumoe-app`

## 目的

macOS では画面上部のメニューバー（システムのネイティブメニュー）にエディタのメニューを出す。Windows / Linux は、いまのウィンドウ内メニュー（egui）のまま。

## 範囲

- 依存の追加: `muda`（最新 0.21.2、2026-10-08 時点）。利用者が追加を了承した（2026-11-01）。`tsukumoe-app` の `cfg(target_os = "macos")` の依存に限り、ほかの OS のビルドに入れない。`deny.toml` のライセンス・重複検査を通す
- メニューの定義を 1 か所にまとめる: 項目（アクション名・ラベルの翻訳キー・有効 / 無効・サブメニュー）をデータとして持ち、egui のメニューとネイティブメニューの両方がそこから作る。いまの `Editor::menu_bar` に直書きされた項目を移す
- 項目の実行はアクション名に統一する。いま直接ダイアログを開く項目（開く・名前を付けて保存・最近使った項目）は、アクション名で呼べるようにする
- ネイティブメニュー（macOS のみ）:
  - アプリメニュー（アプリについて・隠す・終了）とウィンドウメニューは標準のもの（`muda` の定義済み項目）
  - ファイル・編集・表示など、egui のメニューと同じ構成
  - 選んだ項目は `muda` のイベントを毎フレーム取り出し、`Editor::run_action` へ流す
  - 有効 / 無効（保存・undo・redo など）と「最近使った項目」の中身を、状態が変わったときに更新する
  - 言語を切り替えたらラベルを作り直す
  - ショートカットは表示だけ付け、実際に効かせるのは egui のキーマップのまま（ネイティブ側でも効かせると二重に実行される）。割り当てを利用者が変えたら表示も更新する
- macOS ではウィンドウ内の egui のメニューバーを出さない（二重に見えるため）
- 範囲外: Windows / Linux のネイティブメニュー、ドックメニュー（Dock のアイコンの右クリック）、macOS のサービスメニュー

## 方針

- `muda` のメニューは、macOS ではメインスレッドで作り、アプリのイベントループの開始後に取り付ける必要がある。eframe のどの時点で取り付けられるかを最初に検証し、検証の結果を「決めたこと」に書く
- 状態の更新は差分があるときだけ行い、毎フレームの再構築はしない
- ネイティブメニュー部分は薄く保つ。定義の作成・状態の判定・ショートカット表示の文字列は、`cfg` なしの純粋な関数にしてほかの OS でもテストできるようにする
- 自動テストが届かない部分（実際のメニューバー）は、起動して確認した内容を報告に書く

## 検査

- メニュー定義: 全項目がアクション名を持ち、`run_action` で処理できる（未知のアクションがない）。ラベルの翻訳キーが日英で揃っている
- 状態: ドキュメントの有無・undo / redo の可否・最近使った項目の増減に応じて、有効 / 無効と中身が変わる（純粋関数でテスト）
- ショートカット表示: キーマップの割り当て変更が表示の文字列に反映される
- 依存: macOS 以外のビルドに `muda` が入らない（`cargo tree --target` で確認）。`cargo deny` と egui 系・`wgpu` の重複検査が通る
- 実機（macOS）: メニューバーに出る、項目を選ぶと実行される、言語を切り替えるとラベルが変わる、undo の有効 / 無効が変わる

## 受入条件

- [ ] macOS で、メニューバーのネイティブメニューからファイル・編集・表示の項目を実行できる
- [ ] macOS ではウィンドウ内の egui メニューを出さず、ほかの OS では今までどおり出る
- [ ] 有効 / 無効・最近使った項目・ラベル（言語）・ショートカット表示が状態に追従する
- [ ] `muda` が macOS 以外のビルドに入らない

## 決めたこと

- `muda` を使う。macOS のみの依存にする
- 表示は macOS でネイティブ、ほかは egui のまま
- ショートカットの実行は egui のキーマップに一本化し、ネイティブ側は表示だけ
- 取り付けの時点: eframe 0.37 / winit 0.30 では、`run_native` のアプリ作成クロージャ（イベントループ開始後のメインスレッド）で `Menu` を作ってよい。実機で確認した。`init_for_nsapp()` は winit の既定メニューを置き換える。初回の取り付けはクロージャ内ではなく最初のフレームの終わりに行う（メニューの中身がそこで決まるため）
- メニュー定義は `menu.rs` の `MENU`（アクション名とラベルのキー）。`resolve` が状態・翻訳・ショートカットを反映した `Entry` の木にし、egui とネイティブの両方がその木から描く。ネイティブ側は木が前回と等しいときは何もしない（差分があるときだけ作り直す。言語切替・undo の可否・最近使った項目・キー割り当ての変更はすべて木の差分になる）
- アクション名を追加: `file.save-as`、`file.open-recent:<path>`、`view.pie-settings`、`view.drag-settings`、`view.keymap-settings`、`layout.preset.<key>`、`layout.save`、`layout.load:<name>`。キーマップに割り当てられるアクション（`ACTIONS`）には加えない。`run_action` は既知のとき `true` を返す
- ショートカットの表示: `muda` のアクセラレータはキー等価として効いてしまうため使わず、ラベルの後ろに文字列（"⌘Z"）を足すだけにした。egui のキーマップだけが実行する
- ウィンドウ内: macOS ではメニューのボタンを描かず、ワークスペースのタブだけ残す（タブはメニューバーと同じ行にある）。`Editor::native_menu` で切り替える
- アプリメニュー（アバウト・隠す・終了）とウィンドウメニュー（しまう・拡大 / 縮小）は定義済みの項目で、ラベルは翻訳キーから付ける。メニュー項目の `muda` イベントは `set_event_handler` で受けてチャネルに積み、同時にリペイントを要求する（クリックで UI が起きるように）
- 依存: `muda` は `default-features = false`、ワークスペースで `0.21` と指定。`Cargo.lock` に推移依存として `crossbeam-channel`・`keyboard-types` が加わる。`cargo deny check` は通り、例外は不要
- 実機で確認した: メニューバーに出る、ウィンドウ内メニューが消えタブだけ残る、項目の選択で実行される（名前を付けて保存のダイアログ）、プロジェクトを開いている間は保存が有効で undo / redo が無効。未確認: 言語切替での再構築、undo が有効になる遷移（どちらも `Entry` の純粋関数のテストでカバー）
